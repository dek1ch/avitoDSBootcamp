# Поиск кандидатов для объявлений услуг

## 1. Задача и результат

Я решаю этап кандидатогенерации: для каждого поискового запроса выбираю из корпуса до 50 объявлений, которые затем можно передать на ранжирование.
Моя цель — включить в эти 50 объявления, которые выбрал пользователь.

Я беру запросы из `benchmark_queries.parquet`, объявления из `benchmark_items.parquet` и сохраняю результат в `answer.csv`. В файле ровно
две колонки: `query_id` и `answer`. В `answer` я записываю до 50 существующих `item_id` через пробел, без повторов. Скрипт `make_answer.py` создаёт файл,
а `check_answer.py` проверяет его формат. Результат воспроизводится локально без внешних API; версии библиотек указаны в `requirements.txt`.

## 2. Какие признаки я использую

Для текстового поиска я объединяю `search_query` и `search_infm_params_text`. У объявления я объединяю `item_title_raw`,
`item_description_raw` и `item_infm_params_text`. Перед поиском привожу текст к одному регистру и заменяю «ё» на «е».

Использую `search_location_id` и `item_location_id` для отдельного поиска в локации запроса и для бонуса за её совпадение. Остальные признаки
объявления, включая цену и рейтинг, в текущую оценку не добавляю: на этапе кандидатогенерации для меня важно не исключить подходящее объявление
раньше времени. Категорию и признак доставки я не использую для отбора, но учитываю все пять признаков запроса, когда группирую одинаковые
запросы при проверке качества.

## 3. Как я выбрал настройки и устроил поиск

Сначала я проверил обычный текстовый поиск BM25. Без учёта локации в итоговые 50 часто попадали объявления из других городов. Я сравнил
несколько бонусов за совпадение локации на первых 5000 проверочных запросах и выбрал **+8** по Recall@50. На следующих 5000 запросах BM25
без бонуса получил **17,12%**, а общий поиск с бонусом **54,34%**.

Затем я заметил, что некоторые выбранные местные объявления не попадают даже в общий список из 1000 кандидатов. Я добавил отдельный поиск до
50 объявлений в локации запроса. На тех же следующих 5000 запросах Recall@50 вырос до **74,28%**.

После этого я отдельно проверил сочетания размера местного списка и бонуса. На новых 5000 запросах я сравнил размеры 25, 50, 100, 200 и 400
и бонусы от 0 до 32. Лучшим среди проверенных оказался список из **50** объявлений и бонус **+12**. На других новых 5000 запросах этот
вариант получил **75,18% Recall@50** против **74,54%** у прежнего варианта с бонусом +8. Поэтому в итоговом коде я использую +12.

В итоговом варианте я:

1. Нахожу BM25 до 1000 объявлений среди всего корпуса.
2. Отдельно нахожу до 50 объявлений в локации запроса.
3. Объединяю списки и удаляю повторяющиеся `item_id`.
4. Добавляю 12 баллов каждому кандидату из локации запроса.
5. Выбираю до 50 кандидатов с наибольшей итоговой оценкой.

Размеры списков 1000 и 50 определяют, сколько объявлений я рассматриваю до окончательного выбора. Я не исключаю другие локации полностью:
пользователи выбирали и такие объявления.

## 4. Как я проверил Recall@50

В `train.parquet` я знаю, какие объявления пользователи выбрали по своим запросам. Для одинаковых сочетаний признаков запроса я собираю все
разные выбранные `item_id`. Затем считаю, какая их доля попала в найденные 50 объявлений.

На 10 000 разных запросов из середины `train` я получил:

| Способ | Recall@50 |
| --- | ---: |
| Общий поиск и бонус +12 за локацию | 54,55% |
| Общий и местный поиск с тем же бонусом | **74,46%** |

Прибавка составила **19,91 процентного пункта**. Отдельно я проверил 1158 запросов, по которым пользователи выбрали несколько разных
объявлений: Recall@50 вырос с **52,71%** до **76,85%**.

Мои проверочные скрипты — `validate_middle.py`, `validate_repeated.py` и `validate_bm25.py`. Последний выбирает 10 000 случайных разных запросов
с фиксированным зерном и считает общий результат без деления на группы.

## 5. Какие ошибки я нашёл и почему не взял BM25F

Я нашёл две основные проблемы. Без учёта локации BM25 часто поднимал объявления из других городов. Кроме того, часть выбранных местных
объявлений отсутствовала в общем топ-1000. Бонус за локацию помог с первой проблемой, отдельный местный поиск — со второй. Часть выбранных
объявлений всё ещё остаётся за пределами найденных кандидатов.

Я также проверил BM25F, который оценивает заголовок, описание и параметры объявления как отдельные поля. В эксперименте я использовал веса полей
3:1:1. На проверочной группе этот вариант получил **70,30% Recall@50**, а вариант BM25, который я использовал тогда с бонусом +8, — **73,17%**.
Поэтому проверенный вариант BM25F я не включил в создание `answer.csv`.

В итоговом коде я использую открытые библиотеки [BM25S](https://github.com/xhluca/bm25s), pandas, NumPy и PyArrow.
Для отдельного эксперимента с BM25F я использовал PyTerrier; он не нужен для воспроизведения `answer.csv`.

## 6. Как я подготавливаю `answer.csv`

Я кладу `benchmark_queries.parquet` и `benchmark_items.parquet` в одну папку со скриптами. Для запуска проверочных скриптов мне также нужен
`train.parquet`. Исходные Parquet-файлы я не загружаю в GitHub: проверяющий использует данные из задания.

Я устанавливаю зависимости из `requirements.txt`, затем запускаю создание ответа и проверку файла:

```text
python -m pip install -r requirements.txt
python make_answer.py
python check_answer.py
```

После этого я получаю `answer.csv` с одной строкой на каждый запрос бенчмарка. В `answer` перечислены только `item_id` из корпуса, через пробел;
скрипт сохраняет CSV в UTF-8 без дополнительной колонки с индексом.
